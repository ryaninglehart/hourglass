# Incidents

Seven defects found during the build of this pipeline, and three more —
INC-008 to INC-010 — found on 20 August 2026 by a fourth adversarial review
pass after the first public release. All ten are written up the way a team
writes post-incident notes: what happened, how it was found, why it was
possible, and what changed.

A portfolio project keeps an incident log for the same reason a production
system does. Whether a pipeline works today is the least interesting thing
about it — it works today because the person who wrote it was looking at it
today. The question worth answering is what happens when it stops, and a
repository that shows only passing tests has not answered it. Each of these
made it into working code, and eight of the ten produced a plausible result
rather than an error. The exceptions are INC-007, which raised loudly — on a
machine nobody had run it on, which is why it survived the longest — and
INC-008, which raised loudly and then printed a false account of what the
failure had left behind.

Every entry ends with the part most write-ups leave out: the *class* of defect,
and the mechanism that now catches that class without anyone having to remember
it.

**All data in this project is synthetic**, generated by a seeded generator in
this repository. No real patient information was involved in any of these
incidents, because none exists anywhere in the project. Where an entry says
"identifiers leaked", the identifiers were fabricated strings of the form
`CLI-00234`. The control failure was real; the exposure was not.

## INC-001 — Raw identifiers reached published artifacts through quality-check samples

Every quality check attaches a small `sample` of offending rows to its
`CheckResult`, because "3,100 rows are bad" is a statistic and "here are five of
them" is a starting point. Those samples were serialised straight into the
published output.

**Impact.** Raw `client_id` values appeared in `quality_report.json`,
`quality_report.md`, `dashboard_data.json` and `dashboard.html`. `client_id` is
a direct identifier under the HIPAA Safe Harbor list at 45 CFR 164.514(b)(2), so
on real data this would have been an unauthorised disclosure in four files at
once, including the one most likely to be emailed to someone outside the
project. On this data it was five synthetic strings.

**Detection.** An adversarial read of the published bytes — opening the files
the pipeline had just written and searching them for anything that looked like a
source identifier. Not a test run, and not a failing build.

**Root cause.** The de-identification step ran on the *published frames*. The
quality report is not a frame. It is assembled after the checks run, from
objects the boundary never saw, so it left the pipeline through a path the
boundary did not cover. The hole was in exactly the artifact that exists to
describe problems, which is the one nobody thinks of as data.

**Why the tests did not catch it.** There was a regression test. It loaded the
dashboard payload and asserted on `payload["at_risk"]` — the place the author
had thought about. The identifiers were forty lines away in the same file. The
test could not have failed; its shape excluded the defect from view.

**Fix.**

- Redaction moved into `CheckResult.__post_init__`, so every sample is redacted
  at construction. Eleven call sites build samples today — `grep -c "sample="
  src/hourglass/quality.py` — and there will be more; a chokepoint that cannot
  be forgotten is worth more than eleven call sites that currently remember.
- A new `verify` pipeline task re-reads the published files as bytes and scans
  for raw identifier patterns. It runs last, knows nothing about what any file
  means, raises rather than warns, and deletes the offending files. (Since
  INC-008 it restores the previous published build rather than leaving a hole;
  since INC-010 the paths are globbed rather than named.) At the time of this
  fix only the BI CSVs were globbed (`EXPORT_DIR.glob("*.csv")`, eight of them
  today); every
  other path was named one by one, which was a weakness worth stating here rather
  than in a footnote. `metric_parity.md`, `data_diff.md` and `benchmark.md` are
  written to the same directory and nobody added them. `dashboard.html` is
  rendered after the pipeline exits and `pipeline_runs.jsonl` is flushed after
  the task loop ends, so for both the scan opens the previous run's copy. A fix
  that covers most of the exits is the same species of error as the defect.
- `phi_egress` was marked `acknowledgeable=False`. Every other blocking check
  can be released with a written reason; this one cannot, because the others
  protect a number and this one protects a person.
- The PHI classification table and scanner patterns were added to the rule-set
  hash, which had omitted them — meaning a change to the rules that decide the
  `phi_egress` verdict would not have changed the hash that identifies them.
- The regression test was rewritten to read whole files as text, with a
  companion test that plants an identifier in a temporary file to prove the scan
  is capable of failing.

**Class of defect: a control applied at call sites rather than at a chokepoint.**
Now caught by construction-time redaction (so the control cannot be skipped) and
an independent scan of the published bytes (so if it is skipped anyway, the
artifact is still checked). `tests/test_phi.py::TestDefenceInDepth` disables the
redaction, runs the real pipeline, and asserts the `verify` task fails — if that
ever passes, the two layers have collapsed into one and the redundancy is
imaginary.

## INC-002 — The run-over-run diff reported 49,227 changed rows between two identical builds

`diff.py` compares two warehouse builds so a run can be asked "did anything
change, and was it what I expected". Its first version compared columns by
casting them with `astype(str)`.

**Impact.** No published number was wrong. The diff was, and a diff that cries
wolf is worse than no diff: the reader stops opening it, and the real change it
was built to surface goes past unread.

**Detection.** Reading the number and disbelieving it. The pipeline is
deterministic by construction and asserted to be so; a total rewrite of
`fact_session` between two runs of it was not a plausible result. Confirmed by
querying `typeof()` counts on both database files directly and getting identical
answers, which located the fault in the comparison rather than in the data.

**Root cause.** Under pandas 3.0, `astype(str)` leaves `NaN` as `NaN`, and
`NaN != NaN`. Every null cell therefore compared unequal to itself.
`fact_session.unresolved_reason` is null on 49,227 of 52,160 rows — the rows
whose unit of measure resolved cleanly and so have no reason to record. The
diff was reporting the healthy rows as changed.

**Why the tests did not catch it.** The idempotency test passed throughout and
structurally could not have failed. Its checksum writes each table to CSV, and
both a null and a null render as the same empty field, so the test is blind in
precisely the place the bug lives. The two were invisible to each other.

**Fix.** A `NULL_SENTINEL` substituted for nulls before comparison, containing a
NUL byte so no real value can collide with it. A printable sentinel would not
do: `"null"` as a sentinel makes a column that legitimately contains the string
`"null"` compare equal to an absent value, which trades a false positive for a
false negative. Plus `tests/test_diff.py`, which the module had not had — 38
tests, including one asserting the sentinel cannot collide with real data.

**Class of defect: a false positive in a monitoring tool.** It is the failure
mode that destroys the tool rather than the system, because the damage is done
to the reader's attention and is not recoverable by fixing the tool later. Now
caught by a dedicated test file that pins null-to-null, null-to-value and
value-to-null as three distinct outcomes.

## INC-003 — Dtype drift would have been reported as data change

Found while writing the tests for INC-002's fix, before the fix shipped.

**Impact.** None reached a build. This is the one incident here caught before it
could produce a wrong report, and it is included because of how it was found
rather than what it cost.

**Detection.** Writing a test for a claim the module's own docstring already
made. The docstring said dtype differences were handled. They were not: with
every column compared as text, an integer `4` and a float `4.0` are different
strings, so a column would be reported as changed with no change in it.

**Root cause.** A pandas integer column widens to float64 the moment one null
appears in it, and SQLite will hand back `4` from one build and `4.0` from the
next for the same untouched value. Storage disagreed; the data did not. The
string comparison had no way to tell those apart.

**Why the tests did not catch it.** There were no tests for the module at all
until this point — see INC-002. The relevant observation is that the *comment*
had been trusted in place of a test, and a comment asserting a property is
indistinguishable from a comment describing a property that was removed.

**Fix.** Numeric columns are compared numerically, with null equal to null; text
columns go through the sentinel. Datetimes are excluded from the numeric path
deliberately: `to_numeric` will convert them to epoch nanoseconds, but it
renders `NaT` as `-9223372036854775808` — a real, comparable integer — which
would have reintroduced INC-002 wearing a different hat.

**Class of defect: a comment asserting a property the code did not have.** The
cheapest way to find this class is to write a test for each claim the
documentation makes, which is what turned this one up. There is no automated
mechanism here, and that is worth stating plainly: nothing in this repository
checks a docstring against its function.

## INC-004 — Utilisation was computed over cancelled sessions when frames came from the warehouse

`analytics.build_utilization` filtered its sessions with
`fact_session.loc[fact_session["is_completed"] & fact_session["uom_resolved"]]`.

**Impact.** Utilisation, delivered units and delivered hours were computed over
the wrong rows entirely whenever the frames were read back out of the warehouse
rather than handed straight over from `transform.py`. The parity check measured
410,405 units delivered from SQL against 106,764 from pandas — a factor of
nearly four, in the direction of *under*statement, which is the first clue that
"the filter let everything through" cannot be the explanation. Every downstream
consumer that reads the warehouse — the SQL queries, and anything built on the
exports — would have disagreed with the dashboard, and the dashboard was the one
that was wrong.

**Detection.** The first run of the metric parity harness in `metrics.py`, which
had been built to catch a different problem entirely: definitions drifting apart
between `analytics.py`, `sql/analytics.sql` and `bi/measures.dax`. It computes
each registered metric twice — once in SQL against the warehouse, once in pandas —
and compares. It found this on the first execution, before it had ever caught
the thing it was written for.

**Root cause.** SQLite has no boolean type. The frames `transform.py` produces
carry real `bool` columns; the same tables read back out of the warehouse carry
`int64` 0/1. And `df.loc[int_series]` is not a boolean mask. `.loc` is
**label**-based, so pandas reads each element of the mask as an index *label*
and looks it up, returning one row per element — duplicated copies of the rows
labelled 0 and 1. It does not raise.

The arithmetic is worth working through, because it is what makes the reported
figures make sense and it is where an earlier version of this write-up was
wrong. This write-up said the filter "returned every row", which would have made
the pandas number *larger* than the SQL number rather than smaller, and the
recorded numbers refuted it. Reproduced against the current warehouse on pandas
3.0.2: `fact_session` has 52,160 rows, the mask `is_completed & uom_resolved` is
1 on 44,534 of them and 0 on 7,626, and the row labelled `1` is a cancelled
session with zero units while the row labelled `0` is a completed session with
fourteen. So every session that *should have passed* the filter contributed row
1's zero, every session that *should have failed* contributed row 0's fourteen,
and the total was 7,626 × 14 = 106,764 — the exact figure the harness reported.
The selection was not merely unfiltered; it was inverted, and the headline was
computed over two rows repeated fifty-two thousand times.

That distinction matters for more than pedantry. "The filter did not filter"
suggests a number that is too big by a known amount and can be reasoned about.
What actually happened is that the output had no relationship to the input at
all, and the only reason it looked plausible is that row 0 happened to hold a
mid-sized value.

**Why the tests did not catch it.** Every test in the project built its frames
on the transform side, where the columns really are booleans, so the filter
behaved correctly in every test and incorrectly in the pipeline. The tests were
not weak; they were all standing on the same side of the boundary the defect
lived on.

**Fix.**

- An `analytics._flag()` helper that coerces to bool at every flag read, used
  at every place a flag column is filtered on — four at the time of the fix,
  eight today. The count went stale in an earlier revision of this sentence,
  which is this log's own INC-003 lesson applied to itself.
- A test asserting that the boolean and integer paths produce the same
  utilisation, and one asserting a cancelled session stays excluded under
  integer flags (`tests/test_metrics.py`).
- A test that documents the pandas `.loc[]` behaviour itself, pinning what an
  integer mask actually returns. If a future pandas makes that raise, the test
  fails, and the justification for `_flag` gets revisited rather than surviving
  as folklore.
- The parity check now runs as a pipeline task on every build, and it *raises*.
  A disagreement means the published numbers are not reproducible from the
  warehouse they claim to come from, so `publish` is marked skipped and the
  previous build's exports stay in place.

**Class of defect: a correctness property that depends on an upstream dtype
nobody declared.** Now caught by cross-engine metric parity on every run. Note
the limit of that mechanism: SQL and pandas are both executed and compared, but
the DAX measures are checked only by a column contract — the measure must exist
and reference the declared base columns. Two engines are checked by execution
and the third by static contract, and calling that three would be the same
species of error this log exists to record.

## INC-005 — The dashboard's headline tile divided units by four, and the parity check reported agreement throughout

Decision 5 in the README is titled "Hours are never units divided by four". A
unit is fifteen minutes for the ABA codes, thirty for a medical visit and
forty-five for a speech session; `dim_service.minutes_per_unit` carries the
conversion and every hours figure is supposed to go through it. `export.py`
computed the dashboard's "unused hours" tile as `units_unused * 0.25`.

**Impact.** The most prominent number on the analyst view was understated by
**958 hours**, 1.7% of a true 57,763.8. The aggregate error is small because 99%
of the unused units on open authorisations are billed in 15-minute units — the
four ABA codes and the occupational-therapy code — where a quarter-hour happens
to be right. The error is not distributed like the aggregate: at 30 minutes per
unit the tile showed
257.5 hours where the truth was 515.0, and at 45 minutes it showed 350.2 where
the truth was 1,050.8. Speech was displayed at a third of its size and medical
at a half — on the disciplines the at-risk list exists to surface, in a list
ordered by hours. A coordinator reading the tile would have ranked the two
smallest, most fragile service lines last.

**Detection.** An adversarial read of `export.py`, looking for the project's own
stated rules being broken inside the project. Not a test, not a check, and not
the report whose entire purpose is this class of disagreement.

**Root cause.** Two things, and the second is the interesting one.

The tile was a calculation nobody had registered. `metrics.REGISTRY` declares
`hours_unused` and computes it from `utilization["hours_unused"]`, a per-row
column that `build_utilization` derives correctly through `minutes_per_unit`.
The published tile was assembled separately in `export.py` from a different
input by a different route. The two were never the same code and were never
compared.

So `metric_parity.md` read "All 11 metrics agree" for the entire life of the
defect, and it was telling the truth. It compared the SQL implementation of
`hours_unused` against the pandas implementation of `hours_unused`, and both
were right. What it could not do — what no comparison between two
implementations of a definition can do — is notice that the artifact showed a
third number.

**Why the tests did not catch it.** `tests/test_metrics.py` asserts the registry
agrees with itself across engines, which it did. `export.py` has no test file of
its own; what touches the payload does so to check something else — the digest
takes the headline dict as an input fixture, the PHI tests read the file for
identifiers, the pipeline test checks it was written. Nothing in the suite held
a published figure against the warehouse it claims to describe, because every
test that knew the right answer was exercising the code that already had it.

**Fix.**

- The tile sums the per-row `hours_unused` column, so the tile and the registry
  now read the same derivation.
- `metrics.check_published_headlines` re-derives five headline figures in SQL
  directly from the warehouse and compares them against what was actually
  written to `dashboard_data.json`. It runs inside `task_verify`, after the
  files exist, and raises. The comparison is appended to `metric_parity.md`
  under its own heading, so the report distinguishes "two implementations agree"
  from "the number a reader sees is reproducible from the data".
- The tolerance is 0.5 absolute, not the 1e-6 used between engines, and the
  reason is recorded rather than tuned: the payload rounds to one decimal place
  before it is written, so anything tighter than half a rounding step fails on
  the rounding. It was 0.05 for one run and 57,763.75 against a published
  57,763.8 tripped it on float representation alone. Half an hour is three
  orders of magnitude below the error this exists to catch.

**Class of defect: a check verifies the value it names, not the value the reader
sees.** Every check on the *numbers* up to this point compared a definition
against another definition, or a frame against a rule. Only the byte-level PHI
scan from INC-001 read a published artifact at all, and it reads it for
identifiers rather than for values, so it would have found a leaked `CLI-00234`
on the tile and had nothing to say about the figure beside it. A check can be
correct, passing, honestly reported and completely irrelevant to the thing on
the screen, and the passing report is worse than no report — it is an audit
trail attesting to a number nobody displayed. The only mechanism that closes it
is re-deriving the published artifact from the source of truth, which is what
the headline check now does and what INC-001's scan was already doing for a
different property. Note the limit immediately: it covered five figures when
this was written, and the figure a reader sees first — pace — was not among
them, which became INC-009. It covers seven today. The at-risk table, the
per-payer and per-discipline breakdowns and the assumption spread are all
still computed in `export.py` by routes nothing re-derives.

There is a second observation, and it is the uncomfortable one. This rule is
stated in the README as a numbered design decision and in comments in
`analytics.py`, `sql/analytics.sql` and `bi/measures.dax` — four places, each
explaining that a flat divisor understates speech and medical by two to three
times. It was broken anyway, in the file that produces the output, by the person
who wrote all four. A convention documented four times and enforced zero times
is a convention that is not enforced, and the fix that matters is the executable
one rather than a fifth comment.

## INC-006 — The rule-set hash covered every threshold but not the unit-conversion table, and nothing compared it between runs

`quality.ruleset_hash()` fingerprints the rules a verdict was produced under, so
an old verdict cannot be read as a statement about the current ones. It covered
`RULESET_VERSION`, the names of the check functions, nine thresholds and the PHI
rule-set fingerprint. It did not cover `SERVICES` — the table that says a unit is
fifteen minutes for the ABA codes, thirty for a medical visit and forty-five for
a speech session.

**Impact.** Editing one service's `minutes_per_unit` changes every hours figure
in the warehouse by up to a factor of three, and the hash that claims to identify
the rules did not move. Nothing is *invalid* — no check can object, because no
rule was broken and the pipeline cannot know which value was intended — so the
run published, the diff reported 56,223 changed rows, and nothing anywhere said
why they had moved. `EXPIRY_WARNING_DAYS` had the opposite problem: it was in the
hash, and nothing compared this run's hash against the previous one, so the
fingerprint was being stamped on every run and read by nobody. Widening the
at-risk window from thirty days to ninety therefore changed every headline and
tripled the weekly list in complete silence.

**Detection.** `make prove`, the sabotage harness. It applies seven deliberate
single-line breakages and records what each safety net does, and case 7 — the
at-risk window — was declared `expect="nothing"` and printed as an honest blind
spot on every run. The harness did not fail here; it did its job. The finding is
what a blind-spot report is *for*: a limitation stated plainly enough, and often
enough, that somebody eventually asks what it would cost to close rather than
reading it as settled.

**Root cause.** Two, and they compound. The hash omitted a definition because the
comment above the dictionary asks for "every threshold that can change a
verdict", and a unit conversion is not a threshold — it is a definition, and it
changes every number the thresholds are applied to. The rest of the fingerprint
was complete enough to make the omission invisible, which is the failure mode the
comment beside it already names: a partial fingerprint is worse than none,
because it looks like it identifies the rules and does not.

Second, nothing read the value. `run_log.ruleset_hash` is `NOT NULL` in
`star_schema.sql`, so every run that has ever been recorded carries the hash it
ran under, and no code path opened it. A value that is written and never compared
is not a control, it is a column.

**Why the tests did not catch it.** `tests/test_quality.py::TestRulesetHash`
pins that the hash is stable across calls and that it moves when
`UOM_COVERAGE_FLOOR` moves. Nothing pinned the conversion table, and the reason
that gap is not an oversight is worth stating: a test can only pin one input at a
time — change this value, assert the hash changes — which catches a regression in
coverage that already exists and says nothing about an input nobody thought of. A
test enumerating the same list the hash enumerates would have passed for exactly
as long as the hash was wrong.

**Fix.**

- `ruleset_hash()` now includes the unit-conversion table as
  `{service_code: minutes_per_unit}`, and `RULESET_VERSION` went to 1.9.0.
  Verified by substitution rather than by reading — on the rule set as it stands
  under rule set 1.9.0, speech at 45 minutes hashed to `ae0bc03167c6e636` and
  at 15 minutes to `9b346469c255e733`, and a thirty-day at-risk window hashed
  to `ae0bc03167c6e636` against `9fcc5d7b2014131c` for ninety. (Under 1.10.0,
  which added the suppression threshold — INC-010 — the same three are
  `7873731d9d66f3d2`, `d0c6fc87ca748bda` and `5de6a73ed75ed14b`.)
- `task_diff` reads the previous *published* build's hash out of its `run_log`
  (`SELECT ruleset_hash FROM run_log WHERE published = 1 ORDER BY
  finished_at_utc DESC LIMIT 1`) and compares it. A missing value — a first run,
  or a warehouse predating the column — is treated as "cannot tell" rather than
  "unchanged", so an absent hash never produces a false all-clear.
- When the two differ, `data_diff.md` opens with a banner giving both hashes and
  saying that any difference below it may be a change in what the numbers *mean*
  rather than in the underlying care. It is placed above the table deliberately:
  a reader who works this out three tables down has already formed a wrong
  theory. On identical data the report says so explicitly — "no row changed, but
  the definitions did" — because that combination is the one a row count cannot
  express.
- Nothing blocks, and nothing should. A policy constant is not a data error.

That last point is the reason the entry is here rather than in the README's
limitations: the fix is not a gate, it is a sentence addressed to a person, and
the only thing it changes is whether they compare this week's list with last
week's as though the two meant the same thing.

**The harness had itself gone stale, and that is the second half of this entry.**
`prove.py` decides what happened by looking for evidence in the run, and its
detector looked for the string "rows differ" in `data_diff.md`. A definition
change moves every published figure while leaving every warehouse row identical,
so "rows differ" never appears — which meant that after the banner existed, the
harness carried on reporting case 7 as caught by nothing. A blind-spot report
that has gone stale is worse than no report, because it is a document
volunteering a weakness that has been fixed, in the direction that flatters
nobody and misleads everybody. The detector now looks for the banner as well, and
the script asserts its declared outcome in both directions: a safety net that
stops working is a failure, and so is a documented blind spot that has quietly
started being caught.

**Class of defect: an identifier that covers part of what it names, and a report
that describes a state the code has left.** Case 7 moved from "passed silently"
to "reported", and case 5 — a service's minutes-per-unit edited — now carries the
same banner explaining why 56,223 rows moved. The current result, run 20 August
2026: **seven sabotages, four stopped the release, three were reported, none
passed silently.** The harness prints the caveat that belongs with that sweep
rather than leaving it to be inferred — it is a statement about the seven cases,
not about the pipeline, and the blind spots still open are the ones nobody has
thought to sabotage. Nothing here checks that the hash covers the code; the next
threshold added and not registered is this same defect, and `make prove` will
find it only if somebody writes the sabotage for it.

## INC-007 — The fallback for a reviewer with no AWS credentials raised instead of falling back

`ingest.make_backend` prefers S3 and drops to a filesystem mirror with the
identical key layout when S3 is not there, so somebody cloning this repository
with no Docker and no AWS account can still run it end to end. On a machine with
no `~/.aws` directory and no `AWS_*` environment variables, it raised.

**Impact.** `make check` failed on a clean MacBook: 455 passed, 1 failed.
`tests/test_ingest.py::TestBackendSelection::test_falls_back_to_local_when_s3_is_unreachable`
asserted that `make_backend` returns a `LocalLakeBackend` when the endpoint is
unreachable, and got `botocore.exceptions.NoCredentialsError`. No published
number was affected and no data was wrong — `make gate`, `make run` and `make
all` all pass `--no-s3`, so they never construct an S3 client — but
`python -m hourglass.pipeline` prefers S3 by default, and on that machine it
would have raised inside `land`, retried twice more, failed the task and marked
every dependent SKIPPED. The failure fell on precisely the person the fallback
was written for, and on nobody else.

**Detection.** The project was run on a machine it had not been built on. The
question that prompted that is the right one to put to any assistant reporting
that the tests pass — *how can I take your word for it, and how will I know when
it breaks* — and the only honest answer was: don't, run it yourself. It was set
up on a MacBook that had never been configured for AWS, and `make check` was run
there. The defect had survived three adversarial review passes, a 456-test suite
and a mutation-testing run, every one of which had executed in a single
environment: a container with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`
present in the process environment. That detail is the
whole incident: *any* credentials at all, including rejected ones, sign
successfully, fail to connect, and fall back correctly. The only machine that
reproduces this is one that has never been told about AWS.

**Root cause.** botocore signs a request before it opens a socket. With nothing
to sign with, it raises at signing and never reaches the connection error the
fallback was written to catch. `make_backend` caught `EndpointConnectionError`,
`ConnectionError`, `OSError` and a named set of `ClientError` codes;
`NoCredentialsError` is not one of them and is not a subclass of any of them. The
handler was correct for every failure that happens on the wire and blind to the
one that happens before it.

**A second cause, found while fixing the first.** `S3Backend.__init__` built its
client with `boto3.client(...)`, which goes through a module-level default
session that resolves credentials once per process and caches them. Two
consequences, and neither is only a test concern: a long-running process cannot
pick up rotated credentials, and the first caller in a process silently decides
the credentials every later caller gets. The second is why the new test could not
be made to pass deterministically at first — a test that pinned its own
environment still inherited whatever the test before it had resolved, so the
credential handling was unverifiable rather than merely untested. `S3Backend` now
constructs a fresh `boto3.session.Session()` per backend.

**Why the tests did not catch it.** There was a test, it was aimed at the right
property, and it asserted the right thing. It simply never ran anywhere without
credentials: its outcome was a function of the machine rather than of the code,
and the machines it ran on all had them. The version it replaced also declared a
`monkeypatch` fixture it never used — plausibly where dummy credentials were
meant to be set and never were, which left a test that read as though it pinned
an environment while pinning nothing.

**Fix.**

- `NoCredentialsError` is caught and falls back, with the reasoning in the code
  rather than in a commit message: somebody who has never configured AWS is not
  misconfigured, they are not using it, so the local mirror is the correct
  answer and is the commonest way this project will be run by anyone but its
  author.
- `PartialCredentialsError` raises a `RuntimeError` instead, naming the
  misconfiguration and stating both ways out — fix the credentials, or unset
  them entirely. Half-configured is a mistake rather than a choice: an access
  key with no secret means somebody meant to use S3 and got it wrong, and
  falling back silently would hide that behind a run that looks like it worked.
  Rejected credentials are unchanged — `AccessDenied`, `InvalidAccessKeyId`,
  `SignatureDoesNotMatch`, `ExpiredToken` and `UnauthorizedOperation` still
  raise, because writing to local disk and reporting success is the class of
  failure this project exists to argue against.
- `TestBackendSelection` was rewritten so that every test pins the credential
  environment explicitly. `no_aws_credentials` clears eight `AWS_*` variables
  *and* redirects `HOME` and `USERPROFILE`, because botocore reads
  `~/.aws/credentials` as well as the environment — without the redirect the
  fixture asserts nothing on a laptop with a configured profile, which is the
  same defect one layer up. `dummy_aws_credentials` sets a key pair for the
  connectivity path. Five tests, one for each path through the function.

**Class of defect: a correctness property decided by ambient machine state
nobody declared.** Now caught by pinning the credential environment inside the
tests, so the result is a function of the code rather than of the host. The
residual limit belongs in the same breath: this closes one class of environment
variable. `HOME`, `TZ`, `LANG`, an installed binary, a locale that formats a
decimal with a comma, the clock — any of them can decide a result in this
repository and nothing enumerates them. The general problem is not solved, it is
solved for AWS credentials. Worth adding that CI declares no AWS credentials
either — `.github/workflows/ci.yml` passes `PYTHONPATH` and nothing else — so
this was waiting there too. It surfaced on a laptop first only because that is
where the project was next run by somebody who had not built it.

There is a better observation than any of that. "Works on my machine" is
normally a joke about the developer. Here it was a joke about the reviewer: the
one environment the code was never exercised in was the clean one it was written
to accommodate. This whole project argues for checking the artifact rather than
the intention, and the thing nobody checked was the environment the checks
themselves ran in.

## INC-008 — A run that failed after publishing left its own artifacts serving, under a console line saying nothing was published

`task_publish` writes the BI CSVs, the dashboard payload and the digest;
`task_verify` then re-derives the published headlines and raises on a mismatch.
The failure was loud — exit 1, the right word in capitals — and the aftermath
was wrong twice over. The failed run's files stayed on disk, replacing the
previous good set, so anything reading `data/out/` consumed the numbers the
pipeline had just refused to stand behind. And the console printed "Nothing was
published," which was precisely false: everything had been published, and
nothing had been taken back.

The warehouse had the opposite guarantee from the first day — scratch build,
atomic rename, quarantine on refusal, previous build left serving. The exports,
the artifacts a reader actually opens, had none of it.

**Found by.** The fourth adversarial review pass, re-applying INC-005's own
sabotage — restore the flat quarter-hour divisor — and then reading the disk
after the failure instead of the exit code. The wrong payload was still there;
the digest had been rewritten with it.

**Fix.**

- `task_publish` snapshots every file it is about to overwrite. A failure
  anywhere in `task_verify` restores the snapshot before the exception
  propagates: previous bytes back, files with no predecessor removed.
  Asserted by `test_a_failed_verify_restores_the_previous_published_build`.
- The console line is conditional now. A post-publication failure reports that
  this run's artifacts were withdrawn and the previous build still serves,
  which is what actually happened.

**Class of defect: a guarantee implemented for one store and assumed for the
other.** The question that finds the class: for every place a run writes, what
is serving from there after this run fails?

## INC-009 — The headline check covered five figures, and the figure a reader sees first was not among them

`check_published_headlines` exists because of INC-005: re-derive the dashboard's
published numbers from the warehouse, because the parity check attests to
registry definitions and says nothing about the tiles. It covered `hours_unused`,
`units_authorized`, `units_delivered` and the two authorisation counts. It did
not cover pace — the percentage in 64-point type at the top of the page.

A sabotage recomputed pace over every authorisation instead of the open ones.
The dashboard published 76.0% where the true figure was 75.1%, exit 0, nothing
objected. The same review found the pace-by-payer, by-discipline and by-centre
panels were *already* computed over that wrong population, under a subtitle
reading "Same measure": every bar sat up to three points from the hero figure it
claimed to break down, and no reader could have reconciled them.

**Found by.** Extending the sabotage harness with cases nobody had thought to
run, which is what its closing banner says to do.

**Fix.**

- Two figures added to the re-derivation: `expected_units_to_date`, and `pace`
  as SQL date arithmetic mirroring `analytics.build_utilization` — with its own
  tolerance, because the half-unit tolerance that suits summed figures would
  accept literally any value of a ratio.
- The three breakdown panels are computed over the hero's population, so "same
  measure" is now true rather than approximately true.

**Class of defect: INC-005's class, recurring in the same file.** A check
verifies the value it names, not the value the reader sees — and a scope that
lives in a hand-maintained dict re-creates the gap every time the payload grows.
The at-risk table and the assumption spread are still outside it, and the
README says so.

## INC-010 — The rule-set hash's own comment warned that a left-out threshold is worse than none, and one was left out

`quality.ruleset_hash` fingerprints every constant that decides what a run
publishes, so that two builds can be compared knowing whether the rules moved
(INC-006). The comment above its threshold table reads: "One that is left out
makes the hash a partial fingerprint, which is worse than none." The small-cell
suppression threshold was not in the table.

A sabotage weakened `SUPPRESSION_THRESHOLD` from 10 to 2. The run published
previously suppressed counts — the exact disclosure the control exists to
prevent — with exit 0 and an unchanged hash, `ae0bc03167c6e636`. Nothing
in the run's record distinguished it from the build before it.

The same pass found two more instances of the same shape. The byte-scan's file
list was written out by hand and had drifted: `metric_parity.md` and
`data_diff.md` were published, committed to `samples/`, and never scanned,
while the docstring above the scan claimed "every published file." And the
org-wide child count was suppressed in the digest but published raw in
`dashboard_data.json` — one figure, two policies, depending on which artifact
you opened.

**Found by.** The sabotage harness again, aimed at the controls themselves
rather than the data.

**Fix.**

- `SUPPRESSION_THRESHOLD` joined the fingerprint; `RULESET_VERSION` went to
  1.10.0. The base hash is now `7873731d9d66f3d2`, and weakening the threshold
  moves it.
- The scan list is a glob over the export and report directories, so a report
  added tomorrow is scanned by default rather than remembered by somebody.
- The child count is suppressed at the source, in the payload, and the digest
  recomputes the real number from the frame it is handed.

**Class of defect: INC-006's class — a partial fingerprint, and a
hand-maintained list restating what a directory already knows.** Both go stale
silently. The fix in every case is deriving the claim from the thing: hash the
constant, glob the directory.

## Reading across the ten

Four of the first five were found by reading output or source, not by a test. The
diff's row count was implausible, the published bytes contained something that
should not have been there, the parity harness printed two numbers that could
not both be right, and the headline tile contradicted a rule the repository
states four times. Tests encode what you already thought of; they are excellent
at holding a known property still and structurally incapable of noticing a
property you never articulated. INC-001, INC-004 and INC-005 each had a full
suite passing over them.

Two were found by tools built to check something else. The parity harness was
written to stop metric definitions drifting between SQL, pandas and DAX, and it
found a dtype bug on its first run. The test file written to lock down INC-002's
fix turned up INC-003 while it was being written. Both are the same effect: a
tool that reads the system from a new angle finds whatever is visible from that
angle, not only the thing it was aimed at.

The last two were found by mechanisms the first five did not have. INC-006 came
out of the sabotage harness, whose entire output is a list of things that are
*not* caught — and the value of writing that list down is that a limitation on a
page eventually gets read by somebody willing to price it, where a limitation
nobody wrote down is a limitation nobody can act on. It
also showed the failure mode that report has of its own: the harness kept
describing a blind spot the code had already closed, because its detector was
looking for the old evidence. A document that describes a state the code has
left is the same defect as a comment asserting a property the code does not have
(INC-003), one level up.

The three from the fourth pass needed no new classes. INC-008 is INC-001's
question asked of a different store — check the artifact, not the plan.
INC-009 is INC-005's class recurring in the same file. INC-010 is INC-006's
partial fingerprint, predicted by the comment sitting directly above the
defect. A log that keeps absorbing new instances without needing new classes
is measuring something real about where this codebase fails.

INC-007 came from the one place no check in this repository can reach, which is
another machine. It is the sharpest entry here for that reason: every
check in this repository, including the ones written in response to the first
five incidents, had run in exactly one environment, and the property that broke
was one no artifact records. There is no way to read a defect like that off the
source, and no test can find it while the thing deciding the answer is the thing
running the test.

Every fix did one of two things — moved a control to a chokepoint where it
cannot be skipped, or added an independent check of the artifact rather than of
the intention. Redaction moved into a constructor. The egress scan reads bytes
off disk instead of trusting the frames. The parity check recomputes from the
warehouse instead of trusting the frame that produced the dashboard. The
headline check re-derives the tile from the warehouse instead of trusting the
registry that never described it. In each case the new mechanism verifies the
output rather than confirming the plan, which is the only kind of check that
survives someone adding a code path the author of the check never saw.

INC-007's fix is neither, and the exception is worth naming rather than filed
under the pattern. Nothing was added: an input was removed. The tests stopped
reading the credential environment they happened to be running in and started
declaring it, which does not check the output more closely — it narrows what the
answer is allowed to depend on. That is the third move available when a defect
turns on ambient state, and no amount of checking the artifact substitutes for
it, because the artifact was correct on every machine anybody looked at.

INC-005 sharpens that into the rule the first four were circling. A check
verifies the value it names, not the value the reader sees, and the gap between
those two is where a green report does the most damage — because a failing check
sends somebody to look, and a passing one about the wrong number sends them
away.

**The honest limit.** This is a single-developer project running on synthetic
data. There was no on-call rotation, no user impact, no customer, no severity
ladder and no clock. Nothing here was detected by an alert at three in the
morning, and nothing had to be communicated to anyone. Calling these
"incidents" borrows a practice from operations; it does not claim to have run
one. What the practice is worth borrowing for is the discipline of the last
line in each entry — naming the class rather than the instance, and asking what
now catches the class — which is useful at any scale, including one.
